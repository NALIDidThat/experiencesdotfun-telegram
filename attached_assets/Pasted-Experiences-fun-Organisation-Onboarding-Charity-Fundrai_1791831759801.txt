1. OBJECTIVE

Extend Experiences.fun to support charities and other social organisations as first-class organisations within the existing application.

The implementation must introduce organisation-type selection after the user selects Organisation, enable charities to establish verified profiles, and lay the foundations for fundraising campaigns backed by Solana treasury infrastructure using Squads.

The existing application must continue to work without breaking participant accounts, organisation accounts, authentication, experience creation, or other existing features.

Core product principle

There are three distinct concepts:

1. Account type: Participant or Organisation.
2. Organisation type: Charity, School, Community Centre, Business, and other supported categories.
3. Permissions: What an organisation is authorised to do, including hosting experiences, publishing fundraising campaigns, and accessing treasury operations.

These concepts must remain separate throughout the application.

Do not introduce Charity as a third top-level account type.

Primary outcomes

The completed implementation should allow a user to:

1. Open Experiences.fun.
2. Select Participant or Organisation.
3. Select Organisation.
4. Choose their organisation type.
5. Complete the appropriate onboarding flow.
6. Create an organisation profile.
7. Complete any applicable verification requirements.
8. Access functionality appropriate to their organisation type.
9. Allow eligible charities to create fundraising campaigns.
10. Associate an approved campaign with an appropriately controlled treasury.
11. Track donations and campaign progress.
12. Connect funded initiatives to Experiences.fun’s existing experience and impact-tracking functionality.

The implementation must distinguish between functionality that is fully operational and functionality that still requires external integrations, administrative approval, or legal review.

3. ONBOARDING EXPERIENCE

3.1 Initial account selection

Preserve the existing initial account selection screen.

It must continue displaying exactly two options:

Participant

Discover local experiences, participate in initiatives, and build a contribution history.

Organisation

Bring communities together, host experiences, and coordinate local impact.

Do not add Charity, School, Business, or any other subtype to this screen.

Do not change the underlying UserType values.

The existing values must remain:

* participant
* organisation

Existing users must retain their current account type.

3.2 Organisation-type selection

When a user selects Organisation, introduce an organisation-type selection step before collecting organisation profile information.

Create a reusable component named:

OrganisationTypeSelection

Place it in the existing mobile application’s component architecture, following the repository’s established conventions.

The component must:

* Display selectable organisation-type cards.
* Include an icon, title, and short description for each option.
* Clearly indicate the selected option.
* Support mobile and web layouts.
* Include accessible labels and selection states.
* Provide Continue and Back actions.
* Preserve the selected value when navigating backwards.
* Prevent progression without a valid selection.

Supported organisation types

Implement the following initial options:

Value	Display name
charity	Charity
nonprofit	Non-profit
school	School / Educational Institution
community_centre	Community Centre
library	Library
youth_organisation	Youth Organisation
business	Business / Sponsor
other	Other Organisation

Use a single option for Charity and a separate option for Non-profit so the application can collect the appropriate registration information for each.

These values are organisation subtypes, not account types.

Store them using a consistent, validated representation.

Do not allow arbitrary organisation-type strings to be submitted through the API.

3.3 Navigation flow

Implement the following flow:

WELCOME
→ ACCOUNT TYPE

If Participant:

ACCOUNT TYPE
→ EXISTING PARTICIPANT ONBOARDING
→ PARTICIPANT PROFILE
→ PARTICIPANT DASHBOARD

If Organisation:

ACCOUNT TYPE
→ ORGANISATION TYPE
→ ORGANISATION PROFILE
→ VERIFICATION, WHERE REQUIRED
→ ORGANISATION DASHBOARD

Do not introduce the organisation-type selection into the participant flow.

Do not require users to select an organisation subtype when creating participant accounts.

3.4 Authentication compatibility

The repository supports authentication flows that must continue working.

Ensure the new selection works with:

* Existing email signup.
* Existing email login.
* Telegram authentication.
* Existing account creation.
* Existing profile switching.

Do not create duplicate user accounts simply because a user changes their organisation onboarding selection.

The organisation subtype must be persisted against the appropriate organisation profile and restored when the user returns.

If the user leaves onboarding before completing it, preserve the information using the existing persistence patterns where appropriate.

Do not store authoritative organisation metadata exclusively in local application state.

4. DATA MODEL

4.1 Organisation subtype

Extend the canonical organisation data model to include an organisation subtype.

Conceptually:

type OrganisationType =
  | "charity"
  | "nonprofit"
  | "school"
  | "community_centre"
  | "library"
  | "youth_organisation"
  | "business"
  | "other";

This is a proposed type definition. Implement it using the repository’s actual schema and validation conventions.

The organisation subtype must be available to both the mobile application and backend.

4.2 Verification status

Introduce or extend the organisation verification model to support the following states:

type OrganisationVerificationStatus =
  | "unverified"
  | "pending"
  | "verified"
  | "rejected";

Use the existing verification model if it already provides equivalent functionality.

Do not create a second, conflicting verification system.

The verification status must be controlled by authorised backend operations.

A user must not be able to mark their own organisation as verified by submitting a profile update.

4.3 Fundraising permissions

Fundraising access must be modelled separately from organisation type and verification status.

Conceptually, the application needs to distinguish between:

* An organisation that has declared itself a charity.
* An organisation whose identity has been verified.
* An organisation that has been approved for fundraising.
* An organisation that has a configured treasury.
* An organisation that can publish an active campaign.

Do not assume that verifying an organisation automatically grants every financial permission.

Implement explicit permission checks using the existing authorisation architecture.

4.4 Backwards compatibility

Existing organisation profiles may not have an organisation subtype.

Handle these records safely.

Requirements:

* Existing profiles must continue loading.
* Existing participant accounts must remain unaffected.
* Existing organisation accounts must retain their experience-hosting capabilities.
* Missing subtype values must not crash the application.
* Existing verification states must not be silently overwritten.
* Database migrations must preserve existing data.

Where necessary, allow a legacy organisation profile to have an unset subtype until its owner completes the relevant profile update.

Do not automatically classify all existing organisations as charities or businesses.

5. ORGANISATION PROFILE ONBOARDING

Extend the existing Onboarding component to collect information appropriate to the selected organisation type.

Reuse the existing profile fields and validation wherever possible.

5.1 Shared fields

Collect:

* Organisation name.
* Organisation description.
* Contact person’s name.
* City or operating location.
* Country, where supported by the existing model.
* Areas of focus.
* Profile biography or introduction, where applicable.

Do not duplicate information unnecessarily if it is already collected in the existing onboarding flow.

5.2 Charity-specific fields

For charities, collect or support the collection of:

* Legal organisation name.
* Public-facing name, if different.
* Organisation description.
* Country of registration.
* Charity registration number, where applicable.
* Website, where available.
* Primary contact.
* Areas of work.
* Operating location.
* Verification status.

For non-profits, support the appropriate equivalent registration details for the relevant jurisdiction.

Registration numbers must be optional where no equivalent registration scheme exists, but the organisation must not be treated as verified merely because a registration number was supplied.

Keep sensitive verification information separate from publicly displayed profile information.

Do not expose private contact information or verification documents through public organisation endpoints.

5.3 Other organisation types

Initially, schools, community centres, libraries, youth organisations, and businesses can reuse the existing organisation onboarding form.

Only introduce subtype-specific fields when they are necessary.

Avoid building entirely separate onboarding systems for every organisation category.

6. CHARITY DASHBOARD

Introduce charity-specific capabilities within the existing organisation experience.

Do not create a completely separate application.

The dashboard should adapt based on the organisation’s subtype and permissions.

6.1 Initial navigation

For eligible charity accounts, provide the following sections:

1. Overview.
2. Organisation Profile.
3. Experiences.
4. Initiatives.
5. Fundraising.
6. Impact.
7. Settings.

Treasury management should be exposed only where appropriate.

Do not show financial actions to accounts that lack the relevant permissions.

6.2 Overview

Display:

* Organisation verification status.
* Active experiences.
* Active initiatives.
* Fundraising campaign status.
* Funds raised, where applicable.
* Participant engagement.
* Verified impact metrics.

Only display financial metrics derived from reliable, reconciled transaction data.

Do not invent or estimate funds raised using campaign targets or pending payments.

6.3 Initiatives

An initiative represents a project or programme that an organisation wants to deliver.

Examples:

* A neighbourhood clean-up.
* A youth education programme.
* A community skills workshop.
* A food distribution initiative.
* A local environmental restoration project.

Each initiative should be capable of connecting to one or more Experiences.fun experiences.

Reuse the existing experience model wherever possible.

Do not create duplicate experience records solely to represent a funded initiative.

6.4 Fundraising access

The Fundraising section may be visible to eligible charity accounts.

However, creating a campaign must be restricted to accounts that satisfy the relevant fundraising requirements.

For organisations that have not completed verification, display a clear explanation of what is required before fundraising can begin.

Do not allow an unverified organisation to bypass the restriction through direct API requests.

7. FUNDRAISING CAMPAIGNS

Create a fundraising system that allows eligible organisations to raise funds for specific initiatives.

The fundraising system must remain separate from ordinary organisation profile management.

7.1 Campaign creation

A campaign should support:

* Campaign title.
* Campaign description.
* Associated organisation.
* Associated initiative, where applicable.
* Funding target.
* Currency.
* Campaign image or media.
* Campaign start and end dates, where applicable.
* Intended use of funds.
* Public campaign status.
* Donation and transaction totals.
* Associated treasury configuration.
* Impact milestones.

Use the repository’s existing money and database conventions.

Do not represent monetary values using floating-point arithmetic.

Where supported by the chosen payment and token infrastructure, store monetary amounts as integer minor units or exact token base units.

7.2 Campaign statuses

Implement a validated campaign lifecycle.

Recommended states:

* draft
* pending_approval
* active
* paused
* completed
* cancelled

Use these as the target states, adapting them to existing conventions where necessary.

Define which transitions are permitted.

For example:

* A draft campaign can be submitted for approval.
* A pending campaign can be approved or rejected by an authorised actor.
* An active campaign can be paused.
* A completed campaign cannot silently return to an active state.
* A cancelled campaign must not accept new donations.

Campaign status changes must be validated on the backend.

7.3 Campaign API

Introduce fundraising-specific API routes following the existing routing conventions.

Suggested responsibilities:

fundraising.ts

* Create campaigns.
* Retrieve campaign details.
* Update draft campaigns.
* Submit campaigns for approval.
* Publish approved campaigns.
* Pause or complete campaigns.
* Retrieve authorised organisation campaign lists.

donations.ts

* Initiate supported donation flows.
* Record donation attempts.
* Process verified payment events.
* Track confirmed donations.
* Handle failed or refunded payments.
* Reconcile donation records.

treasuries.ts

* Associate an organisation with an approved treasury.
* Retrieve treasury metadata.
* Monitor treasury-related transactions.
* Initiate authorised treasury operations where supported.
* Track transaction and reconciliation status.

These are proposed responsibilities, not confirmed existing files.

Inspect the repository before creating them, and reuse any existing equivalent functionality.

Do not place the entire fundraising system in accounts.ts.

8. SOLANA SQUADS TREASURY INTEGRATION

Use Squads as the multisig treasury infrastructure for eligible organisations.

Official documentation:

https://docs.squads.so/

Inspect the current Squads SDK and treasury APIs before implementing the integration.

Do not assume that a proposed SDK method or transaction flow exists without verifying it.

8.1 Treasury architecture

The intended relationship is:

Organisation
→ Fundraising Permissions
→ Fundraising Campaign
→ Associated Treasury
→ Confirmed Donations
→ Approved Treasury Operations
→ Initiative Delivery
→ Verified Impact

Each organisation must be associated with the correct treasury.

Do not associate every charity with a single shared treasury by default.

The application must distinguish between an organisation’s treasury and the individual campaigns that it runs.

8.2 Treasury metadata

Store the minimum necessary metadata to associate an organisation with its treasury.

Depending on the integration, this may include:

* Organisation ID.
* Network or cluster.
* Treasury public key.
* Treasury configuration status.
* Creation or association timestamp.
* Relevant transaction signatures.
* Integration status.

Never store private keys, recovery phrases, or signing secrets in ordinary organisation records.

8.3 Treasury approval

Treasury operations must follow the actual authorisation and approval rules configured for the relevant Squads multisig.

Do not assume that a transaction submitted by the application has been approved or executed.

Distinguish between:

* Operation requested.
* Transaction constructed.
* Approval pending.
* Transaction executed.
* Transaction failed.

Only report execution after verifying the relevant transaction state.

8.4 Donation collection

Do not assume that every donation should be sent directly into a Squads treasury without considering the payment flow.

Implement the appropriate collection and settlement architecture for the supported donation methods.

For Solana-native donations, determine how the receiving treasury address, supported assets, transaction verification, and reconciliation will work.

For card or other fiat donations, use a suitable payment provider and implement its required settlement, webhook, and reconciliation flow.

Do not fabricate successful donation records from client-submitted transaction signatures alone.

Verify transactions through a trusted server-side process.

8.5 Security boundaries

The integration must:

* Keep private keys out of the database and frontend.
* Avoid exposing privileged treasury operations to ordinary users.
* Validate the organisation’s authorisation for every treasury action.
* Verify relevant on-chain transactions.
* Prevent duplicate transaction processing.
* Record an audit trail for privileged operations.
* Handle failed, pending, and confirmed transactions distinctly.
* Avoid claiming that funds are available before settlement or confirmation.

Use the current Squads documentation to determine which operations can be executed directly and which require multisig proposals or approvals.

If a complete treasury integration requires additional credentials or external configuration, implement the appropriate integration boundary and clearly document the outstanding setup.

9. DONATION RECORDS AND RECONCILIATION

Donation records must be separate from campaign records.

A campaign can exist before it receives any donations.

A donation can be initiated without being successfully completed.

The application must represent these situations accurately.

9.1 Donation record

The target donation model should capture:

* Donation ID.
* Campaign ID.
* Organisation ID.
* Donor reference, where appropriate.
* Payment method.
* Asset or currency.
* Amount.
* Transaction or payment-provider reference.
* Payment status.
* Creation timestamp.
* Confirmation timestamp, where applicable.
* Refund status, where applicable.

Avoid collecting unnecessary personal information about donors.

9.2 Payment states

Use an explicit lifecycle for donations, covering the applicable states:

* Pending.
* Confirmed.
* Failed.
* Refunded.

Additional states may be required by the payment provider or settlement process.

Do not count pending, failed, or refunded payments as successfully raised funds.

9.3 Idempotency

Implement idempotent processing for payment events and blockchain transaction observations.

Processing the same event twice must not create two donations or double-count campaign totals.

Use database constraints and transactional updates where appropriate.

Do not rely exclusively on frontend checks to prevent duplicates.

9.4 Financial reconciliation

The campaign’s displayed totals must be derived from authoritative donation records.

Where relevant, distinguish between:

* Gross donations.
* Fees.
* Refunds.
* Net proceeds.
* Funds received by the treasury.
* Funds available for an initiative.

These values are not necessarily identical.

Do not report them as interchangeable.

10. IMPACT AND EXPERIENCES INTEGRATION

Fundraising should be integrated into the core Experiences.fun product rather than becoming a disconnected donation directory.

The intended lifecycle is:

Create → Fund → Coordinate → Execute → Verify → Measure → Report

10.1 Initiative milestones

Support milestones for funded initiatives.

A milestone should be capable of recording:

* Title.
* Description.
* Target outcome.
* Associated initiative.
* Target completion date, where applicable.
* Current status.
* Evidence or supporting records.
* Verification status.

Reuse existing experience milestones if they support the required functionality.

Do not create a parallel milestone system unnecessarily.

10.2 Experience connections

Allow an initiative to reference the Experiences.fun experiences used to execute it.

For example, a charity could launch a campaign to raise funds for a neighbourhood clean-up programme.

The charity could then organise several clean-up experiences, recruit participants, verify participation, and report the resulting impact.

Use existing participation and completion-verification functionality where possible.

10.3 Impact reporting

Allow organisations to report:

* Funding received.
* Initiative expenditure, where appropriately supported.
* Experiences delivered.
* Participants involved.
* Verified contribution records.
* Completed milestones.
* Measured outcomes.

Clearly distinguish self-reported outcomes from independently or otherwise verifiably confirmed outcomes.

Do not automatically treat participation counts, XP, or campaign expenditure as proof of social impact.

11. AUTHORISATION AND SECURITY

Security must be implemented in the backend, not merely through hiding buttons in the interface.

11.1 Organisation ownership

Every organisation-specific mutation must verify that the authenticated user is authorised to manage the relevant organisation.

A user must not be able to modify another organisation by changing an ID in a request.

11.2 Verification

Only authorised administrative or verification workflows may change an organisation’s verification status.

Do not allow the client to submit:

verificationStatus: "verified"

and have that value accepted as authoritative.

11.3 Fundraising permissions

Campaign creation, approval, publication, donation administration, and treasury actions must have explicit permission checks.

Where an organisation has not been approved for fundraising, the API must reject attempts to publish campaigns or perform restricted financial actions.

11.4 Audit logging

Record security-relevant actions, including:

* Verification decisions.
* Fundraising approval decisions.
* Campaign publication.
* Treasury association changes.
* Privileged financial operations.
* Administrative changes to organisation permissions.

Do not log passwords, authentication tokens, private keys, or unnecessary sensitive personal information.

11.5 Legal and operational requirements

Do not represent the application as legally authorised to process charitable donations simply because a campaign can be created.

Before enabling real-money fundraising, document the requirements for the intended jurisdictions and payment methods.

For UK operations, investigate applicable charity registration requirements, payment-provider requirements, Gift Aid eligibility, AML/KYC obligations, safeguarding considerations, data protection, and relevant financial-services or cryptoasset rules.

Do not implement Gift Aid claims or imply eligibility without the necessary supporting workflow.

The initial implementation may support campaign setup and test transactions before real-money fundraising is enabled.
